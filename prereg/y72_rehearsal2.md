# Pre-registration: Y72 rehearsal2, a fresh, once-only rehearsal pool (vyra-y72-rehearsal2-fresh-v1)

This record was registered before any treatment update existed and before any scoring of the treatment. This step was CPU only.
A run package, notebook, GPU run, Kaggle dataset or upload each needs a separate explicit approval from AJ.
The machine-readable record is `y72_rehearsal2.json`; the evidence is in `y72_rehearsal2/`.

## Why

The cont400 diagnosis (`docs/Y72FIX2_CONT400_SWING_DIAG.md`, b9926d6) found the following:
- The fixed 40-row Y72 rehearsal was memorized (CE 0.0057 at 350).
- The clipped replay pull then starved: 0.15, with 16 of 25 updates below 0.1 in 351-375.
- Its held-out transfer was weak, so X drove the step and Y72 fell from 504 to 396.

Retuning the clip was not warranted. The thing to change is the signal itself.

## The one change

The control is the cont400 run. Everything else stays the same as in the control:
- the same checkpoint_300 and the same exact restore;
- the same plan 301..400 and the same per-task clip (0.5, lambda 0.25);
- the same evaluation, the same 600-set, and the same gate checkpoints 350/375/400.

Only the 2 replay rows per update change:

| | rows at update u | presentations per row in 301..400 |
|---|---|---|
| control | (2s+j) % 40 of the fixed 40-row set | 5 |
| treatment | 2(u-301)+j of the fresh pool F200 | exactly 1 |

**F200** has 200 Y72 rows (1000 segments):
- Generated by the existing Experiment-Y generator, extracted verbatim as for the 600-set; the extraction reproduces the shipped rows exactly.
- New seeds 20264672 + 100k (k = 0..4). None of them appears anywhere else.
- Ban set of 11189 payloads, which includes the 600-set, every train_Y payload (including the 200-set) and the 40 rehearsal rows.
- Canonical sha256 `d4315c33...76d8`, payload-list sha256 `c860f59b...dc4b8`. It is deterministic: two regenerations gave identical hashes.

**Disjointness.** No overlap with the 600-set or any other eval set:
- 0 shared payloads;
- 0 exact rows;
- 0 shared 16-byte and 32-byte windows;
- no pool payload appears anywhere in the 600-set rows.

The pool shares only the generator and the corpus filler source with the 600-set, the same way the original training rows did. Drawing rehearsal from the 600-set was rejected, because then the hold gate would measure memorization.

**Why it cannot be memorized.** Each row is seen once, so its loss at presentation is a held-out loss. Measured at the control checkpoints, on rows not yet seen:

| | 300 | 325 | 350 | 375 | 400 |
|---|---|---|---|---|---|
| pool CE / 200-set CE | 0.88 | 0.88 | 0.95 | 0.85 | 0.78 |
| 40-row set CE / 200-set CE | 0.06 | 0.05 | 0.05 | 0.08 | 0.07 |

**Clip and lambda are kept.** With fresh rows, the clip binds on 76-100% of probed updates at 300-375, so replay already sits at the 0.5 cap, at parity with X. Changing tau would add a second change.

## Design measurements

All measurements were taken on the control's checkpoints, CPU only, read-only, with nothing trained.

The held-out proxy is the **200-set** (not gated). **The 600-set was not used in any design measurement.**

For each state below, the probe covers the 25 updates that follow it. The table reports the per-update 2-row replay gradient: its clipped contribution and its preconditioned cosine to the held-out gradient.

| state | contribution median (control rows / pool) | updates < 0.1 of 25 | cos(Pg, g_200set) | X64 cost per unit Y benefit |
|---|---|---|---|---|
| 300 | 0.046 / 0.5 | 17 / 2 | 0.067 / 0.109 | 0.67 / 0.98 |
| 325 | 0.028 / 0.5 | 16 / 3 | 0.072 / 0.125 | 1.39 / 1.42 |
| 350 | 0.069 / 0.5 | 13 / 1 | 0.052 / 0.094 | 1.57 / 2.50 |
| 375 | 0.5 / 0.5 | 8 / 0 | 0.137 / 0.140 | 0.93 / 0.88 |
| 400 | 0.008 / 0.14 | 21 / 8 | 0.018 / 0.030 | 4.48 / 11.81 |

**Rejected designs:**
- **Error-weighted (the 2 hardest of the 40 rows).** Its direction carries almost nothing of held-out Y72 at 350 (cos 0.006) or 400 (cos 0.002).
- **Rotating the same 40 rows.** This is what the control did.
- **Original train rows.** Only 8 exist, so this would be memorized faster.
- **Overlapping the 600-set.** This contaminates the gate.
- **A larger pool cycled more than once.** For these 100 updates it is identical to F200; beyond 400 it would need new registered blocks.

## Gates (600-set; unchanged from prereg/y72fix2_cont400.json)

All comparisons use integers with `>=`.
- **R hold:** the sum of Y72 600-set segment-exact over 350/375/400 is >= 1440, and every one of those checkpoints is >= 432.
- **A progress:** X64 held-out exact is >= 44 at 350/375/400, and X64 tokens_correct at 400 is >= 1723 of 1920 (+3.0 pp from 1665).
- **N:** X32 >= 128 and X109 >= 90 at every gate checkpoint.

Verdicts:
- SUCCESS = R and A and N.
- FAIL_PROGRESS = R, not A, N. This means the collapse was stopped but X64 did not progress.
- Other combinations follow the cont400 verdict table.

Non-gating manipulation checks, read from the run's own clip record:
- **M1:** every 25-update window has a median replay contribution >= 0.10 (control: 0.095 / 0.202 / 0.072 / 0.217).
- **M2:** every window has a median replay loss >= 0.005 (control: 0.0044 / 0.0079 / 0.0039 / 0.0038).
- **M3:** every pool row is used exactly once.

## Expected effect and noise

**Supported:** the treatment removes the replay starvation that came before the control's collapse, and its direction is better aligned with held-out Y72. The predicted 600-set outcome is no checkpoint below 432 and a sum >= 1440.

**Not supported, and not claimed:** a calibrated gain in segments.
- The probe is first-order and counterfactual (it is measured at the control's states).
- There is only one control trajectory.
- The parent run slid 524 -> 496 in 276-300 without a starved window.

**Noise** (`y72_rehearsal2/noise_math.json`, Monte Carlo with the measured noise: single SD 9.5, mean-of-3 SE 8.3-9.0, so intra-run correlation 0.64-0.85).

P(R pass) for a flat true level:

| true level | 470 | 475 | 480 | 485 | 490 | 496 | 505 |
|---|---|---|---|---|---|---|---|
| P(R pass) | 0.11-0.13 | 0.27-0.29 | 0.50 | 0.71-0.73 | 0.87-0.89 | 0.96-0.97 | >= 0.997 |

The gate separates the outcomes that matter:

| true profile | P(R pass) |
|---|---|
| the control's 504/396/573 | 0.000 |
| a single dip to 440-460 with the other checkpoints near 500-520 | about 0.77 |
| a parent-like slide 480/464/448 | 0.03-0.04 |

X64 token gain SD is 21. P(tokens >= 1723) by true gain:

| true gain | 0 | 40 | 58 | 80 | 120 |
|---|---|---|---|---|---|
| P(pass) | 0.003 | 0.20 | 0.51 | 0.86 | 0.999 |

For exact >= 44 at all three checkpoints: 0.15 at a flat 44, 0.64 at 50, 0.92 at 55.

**X64 is expected to be harder than in the control.** The fresh signal's first-order X64 cost is 1.8-8.9x the control rows' at 300-375. At 3 of those 4 states it costs at least as much X per unit of Y benefit, because the held-out Y72/X64 conflict (cosine about -0.8) is unchanged. The control gained no tokens.

The most likely outcome is FAIL_PROGRESS. That would confirm the mechanism and isolate the remaining limit as the structural Y72/X64 conflict. This design is a Y72-collapse test, not an X64 progress plan.
